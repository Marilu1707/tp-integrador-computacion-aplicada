1. Objetivos y escenario

Palermo Cloud es una empresa ficticia de hosting. Un cliente nos entrega su servidor Debian sin la clave de administrador y nos pide dejarlo listo para producción. Ese pedido coincide con las consignas del trabajo práctico.

Objetivos

  • Recuperar el acceso de root (clave palermo) e identificar el equipo como TPServer.
  • Actualizar el sistema a Debian 12 "Bookworm".
  • Permitir el acceso remoto de root por SSH con clave pública/privada.
  • Publicar el sitio (index.php y logo.png) con Apache + PHP y cargar la base db.sql en MariaDB.
  • Configurar una IP estática en la misma red que la máquina física.
  • Agregar un disco de 10 GB con dos particiones montadas automáticamente: /www_dir (3 GB) y /backup_dir (6 GB).
  • Programar backups automáticos con un script propio y cron.
El paso a paso completo, con cada comando comentado, está en la carpeta docs/ del repositorio. Los archivos de configuración finales, explicados línea por línea, están en config/.

2. Configuración del entorno

Importación de la máquina virtual

Unimos las partes .rar con WinRAR (extrayendo la primera parte) e importamos el archivo resultante en VirtualBox (Archivo → Importar servicio virtualizado). Antes del primer arranque configuramos la red en Adaptador puente, para que la VM quede en la misma red que la máquina física.

Blanqueo de la clave de root

Como la clave de root era desconocida, editamos el arranque desde GRUB (tecla e): reemplazamos ro quiet por rw init=/bin/bash y arrancamos con F10. Así obtuvimos una consola de root sin contraseña, con el disco en lectura-escritura.

# En la consola que abre init=/bin/bash
passwd              # nueva clave: palermo
exec /sbin/init     # continúa con el arranque normal de Debian

Hostname

hostnamectl set-hostname TPServer   # guarda el nombre en /etc/hostname
nano /etc/hosts                     # línea 127.0.1.1 → TPServer

3. Servicios

3.1 Actualización a Debian 12

Primero actualizamos la versión instalada; después cambiamos el nombre de la versión por bookworm en /etc/apt/sources.list y completamos la actualización. Debian no permite saltear versiones, por lo que desde Debian 10 el proceso se hace dos veces (10 → 11 → 12).

apt update && apt full-upgrade -y          # dejar al día la versión actual
sed -i 's/bullseye/bookworm/g' /etc/apt/sources.list   # apuntar a Debian 12
apt update                                 # leer los repositorios nuevos
apt upgrade --without-new-pkgs -y          # primera pasada, conservadora
apt full-upgrade -y                        # completar la actualización
reboot

3.2 SSH con clave pública/privada

Instalamos openssh-server y autorizamos la clave pública disponible en el home de root. En /etc/ssh/sshd_config.d/tp.conf configuramos PermitRootLogin prohibit-password: root puede ingresar, pero solo con clave, nunca con contraseña.

mkdir -p /root/.ssh && chmod 700 /root/.ssh
cat /root/id_rsa.pub >> /root/.ssh/authorized_keys   # autorizar la clave pública
chmod 600 /root/.ssh/authorized_keys
sshd -t && systemctl restart ssh                      # validar y aplicar

# Desde la máquina física:
ssh -i id_rsa_tp root@IP-DE-LA-VM

3.3 Apache con PHP

apt install -y apache2 php libapache2-mod-php php-mysql

libapache2-mod-php permite que Apache ejecute los archivos PHP; php-mysql, que PHP se conecte a MariaDB. Debian 12 instala PHP 8.2, que cumple el requisito de "7.3 o superior". Copiamos index.php y logo.png a la carpeta web y eliminamos el index.html de bienvenida, que Apache prioriza.

3.4 MariaDB

apt install -y mariadb-server
mysql < /root/db.sql              # redirección de entrada: mysql lee el script
mysql -e "SHOW DATABASES;"        # verificar la base creada

4. Configuración de red

Con ipconfig en la máquina física identificamos el rango de red, la máscara y la puerta de enlace, y elegimos para la VM una IP libre del mismo rango. Configuramos la interfaz como estática en /etc/network/interfaces:

allow-hotplug enp0s3
iface enp0s3 inet static        # IP fija (antes: dhcp)
    address 192.168.0.150       # ADDRESS: IP de la VM
    netmask 255.255.255.0       # NETMASK: máscara de la red
    gateway 192.168.0.1         # GATEWAY: router de salida a Internet
Reemplazar por los valores reales de la red donde se hizo el TP.

Agregamos los servidores DNS en /etc/resolv.conf y aplicamos con systemctl restart networking. Verificamos con ip a, ip route y ping al router, a Internet y desde la máquina física.

5. Almacenamiento

Disco y particiones

Agregamos en VirtualBox un disco VDI de 10 GB, que Linux reconoce como /dev/sdb. Con fdisk creamos dos particiones primarias de tipo 83 (Linux) y les dimos formato ext4.

ParticiónTamañoTipoSistema de archivosPunto de montaje
/dev/sdb13 GB83 Linuxext4/www_dir
/dev/sdb26 GB83 Linuxext4/backup_dir
fdisk /dev/sdb            # n, p, 1, Enter, +3G · n, p, 2, Enter, +6G · p (ver) · w (guardar)
mkfs.ext4 /dev/sdb1       # formato ext4
mkfs.ext4 /dev/sdb2
mkdir /www_dir /backup_dir

Montaje automático

Declaramos ambas particiones en /etc/fstab usando su UUID (obtenido con blkid), que no cambia aunque se agreguen o reordenen discos. Probamos con mount -a antes de reiniciar.

UUID=<uuid-sdb1>  /www_dir     ext4  defaults  0  2
UUID=<uuid-sdb2>  /backup_dir  ext4  defaults  0  2

Apache en /www_dir

Copiamos index.php y logo.png a /www_dir, cambiamos el DocumentRoot en 000-default.conf y agregamos en apache2.conf un bloque <Directory /www_dir/> con Require all granted, sin el cual Apache responde 403 Forbidden.

Registro de particiones

/proc/partitions pertenece a un sistema de archivos virtual que el kernel genera en memoria y se pierde al apagar; guardamos una copia persistente con una redirección:

cat /proc/partitions > /opt/particion

6. Backup automático

Desarrollamos /opt/scripts/backup_full.sh (permisos 750). El código completo y comentado está en scripts/backup_full.sh del repositorio.

RequisitoSolución
Nombre con fecha AAAAMMDDdate +%Y%m%d → <carpeta>_bkp_<fecha>.tar.gz (ej.: log_bkp_20241102.tar.gz)
Guardar en /backup_dirEs el destino que recibe el script; cron siempre usa /backup_dir
Argumentos origen y destino$1 y $2; si no son exactamente dos, muestra un error y sale con código 1
Opción de ayuda-help (también -h y --help)
Validar los sistemas de archivosQue la carpeta exista, que df pueda leer su sistema de archivos y, si figura en /etc/fstab, que esté montada (mountpoint -q)
Compresióntar -czpf con -C, para guardar rutas relativas y conservar permisos

La validación de montaje evita un error silencioso: si la partición de /backup_dir no está montada, la carpeta existe igual sobre el disco del sistema y el backup se guardaría en el lugar equivocado.

Programación con cron

0 0 * * *      /opt/scripts/backup_full.sh /var/log /backup_dir >> /var/log/backup_full.log 2>&1
0 23 * * 1,3,5 /opt/scripts/backup_full.sh /www_dir /backup_dir >> /var/log/backup_full.log 2>&1

La primera línea corre todos los días a las 00:00 y la segunda los lunes, miércoles y viernes a las 23:00. La salida y los errores (2>&1) se agregan a un log. La consigna menciona /var/logs; en Debian el directorio es /var/log, como confirma el ejemplo de la propia consigna (log_bkp_...).

7. Entregables

Con scripts/empaquetar_entregables.sh comprimimos por separado /root, /etc, /opt, /www_dir y /backup_dir. /var, el directorio más pesado, se comprimió y se cortó en partes de 45 MB con split, porque GitHub no acepta archivos de más de 100 MB. Los archivos se copiaron a la máquina física con scp, usando el mismo acceso SSH con clave, y se subieron a la carpeta entregables/ del repositorio junto con sus huellas SHA-256.

tar -czpf - -C / var | split -b 45M -d -a 2 - var.tar.gz.part-   # comprimir y cortar
cat var.tar.gz.part-* > var.tar.gz                               # volver a unir

8. Conclusión

El servidor TPServer quedó actualizado a Debian 12 y accesible de forma segura: root ingresa por SSH únicamente con su clave. El sitio del cliente funciona con Apache y PHP 8.2 sobre una base MariaDB, y responde siempre en la misma dirección gracias a la IP estática.

Separar la web y los backups en particiones propias protege los datos ante problemas del disco del sistema, y el montaje por UUID asegura que el esquema se mantenga en cada arranque. El script de backup valida que los sistemas de archivos estén disponibles antes de copiar y, con cron, genera copias diarias de los logs y tres copias semanales del sitio sin intervención manual.

Además del resultado, el trabajo nos permitió integrar en un caso concreto los temas de la materia: el arranque y la administración de usuarios, el gestor de paquetes, los permisos, las redirecciones, el sistema de archivos y la automatización de tareas.
